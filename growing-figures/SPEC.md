# 成長する図形（背景デザイン）— 仕様

最初のメニューの背景に敷き、練習を重ねるほど育つ模様。
ねらいは「規則は感じるが全体は掴みきれない」図形を、児童の練習量に結びつけて少しずつ開いていくこと。

- 実装の正本：このフォルダの `generators.js`（図形）と、各サイトの共通エンジン（算数タイムアタックは `common/index.html` の「背景の床」）
- 見本帳：`sampler.html`（図形・色2・サイトの速さを切り替えて育ち方を見比べる）
- 検査：`node growing-figures/check.cjs`（採否の基準のうち機械で測れる部分）
- 新しい図形を足す手順：`ADD_PATTERN.md`
- サイトごとの色2の台帳：`COLORS.md`

## 1. 育ち方（3層）

```
無地 → ① 輪郭線 → ② 色1（学年の色）で cls=1 のタイルを塗る → ③ 色2（サイトの色）で cls=0 のタイルを塗る
```

- どの層も「育ち始める点」から近い順に広がり、**画面全体を覆い終えたら次の層へ進む**
- タイルは**必ず1枚まるごと**描く。半分だけ塗られたタイルは作らない（途中で切る円形の切り抜きは使わない）
- ①の途中だけ、輪郭の先にうっすら次の輪郭をにじませる（この先にまだ何かある、という予告）
- 全部そろったら止まる（次の周回は未定）
- 育ち始める点：横長の画面は左下寄り（幅14%・高さ78%）、縦長は上端中央（高さ6%）。
  中央に置くとメニューのカードの陰になり、最初の成長が見えないため
- **起点（図形の中心・育ち始める点）は一つでなくてよい**（利用者の方針。どの図形にも当てはまる）。
  図形の幾何の中心（渦の中心、同心円の中心など）と、育ち始める点は別のもので、どちらも複数あってよい。
  例：二心の渦は2つの中心を持つ。ファレイの円盤は円の中心を画面中央に置き、育ち始める点とずらしている。
  いまの差し替え口は育ち始める点を1つ（`ox, oy`）で渡し、エンジンがそこからの距離で育つ順を決める。
  起点が複数の図形は、生成器がタイルごとに育つ順の値を返す（下の「生成器の差し替え口」の `o`）。最初の例は円と球（circlesphere）

## 2. 育ちやすさ ― 「標準の分数」で揃える

正答の数で育てると、解きやすい問題のサイト（九九：1分30問）は解きにくいサイト（単位換算：1分8問）の数倍の速さで染まる。
練習した時間に対して公平でないので、**正答をそのサイト・そのモードの平均の速さで割った「標準の分数」で育てる**。

```
標準の分数       = Σ（モードごとの本番の累計正答 ÷ そのモードの1分あたり平均正答）
床の枚数         = 標準の分数 × 20 × 1正答あたりの育ち（教師が設定。既定 0.75 枚）
1正答の枚数      = 1正答あたりの育ち × 20 ÷ そのモードの1分あたり平均正答
1分あたり平均正答 =（そのモードの本番の累計正答 ＋ 20×10）÷（遊んだ分数 ＋ 10）
```

- 教師が決めるのは「1分に20問解ける速さの問題を1問正解したときの枚数」。20 は固定の基準で、サイトの平均ではない
  （サイトの平均を基準にすると、どのサイトでも平均の1問が同じ枚数になり、サイトをまたいだ「解きにくいほど染まりやすい」が消える）
- 以前は「標準の1分あたりの枚数」（既定 18）を設定させていた。1正答あたりの方が教師に読みやすいので改めた（18 ＝ 0.75 × 20）

- 平均は**そのサイト自身の記録**（全児童・全制限時間の本番）から出す。サイトごとに別のスプレッドシートなので、自動でサイトごとに揃う
- 「＋20×10 / ＋10」は記録の少ない年度初めの下駄（1分20問を10分ぶん）。記録が増えるほど実際の速さに寄る。単元が別の目安を宣言してもよい
- 結果：**解きにくい問題を載せたサイト・モードほど1問で多く染まり、平均的な速さなら1分の練習でどのサイトも同じだけ育つ**
- 練習（記録しないもの・時間制限つき練習）は数えない。★（自己ベスト更新回数）と同じ理由で、記録しない場で増えると意味が薄れる
- 既知の性質：平均が上がると（学級全体が速くなると）同じ正答の重みが少し減り、床がわずかに戻ることがある
- 既定値の目安：Chromebook の画面でタイルは約2,200枚。3層で約4,400枚ぶんなので、0.75枚/正答なら1分20問の速さで約5,900問（約5時間の練習）で全部そろう

## 3. 色

- 色1＝学年の色。色2＝**サイトごとに別の色**（`COLORS.md` の台帳）。どのサイトの床かが色で分かる
- 色2は宝石の名の8色（`COLORS.md`）から選ぶ。床は薄く塗る背景で意味を伝える色ではないので、
  進み・まちがい・「？」の印の色（色覚の見分けを検査した組）には縛らない。ただし学年の色と同じ色は禁止
- 同じ色の中で、タイルの向きなど（`dir` 0..4）ごとに明暗を5段ずらし、宝石の切子面のように見せる
- 濃さ：色1 30%、色2 26%、輪郭 18%（紙の地 #F7F7F4 の上）。前面の文字とカードを邪魔しない濃さに抑える
- 最初に試した「ミント＋桃」は「不気味」と判断され、宝石感のある組（ミント＋すみれ）に替えた

## 4. 文字の際

タイトル・カード・ボタンの外側 10px の範囲で模様を薄める（最も薄いところで元の10%）。
タイルごとに「一番近い要素までの距離」から濃さを決める。タイル単位なので、際はタイルの形の段差になる。

## 5. 軽さ（児童端末：4GB の Chromebook を前提）

- 描くのは状態が変わった時だけ。常時動くループは持たない
- 同じ色・同じ濃さのタイルを1本のパスに集めて1回で塗る（濃さは40段階に丸める）。1枚ずつ色を切り替えると、それが重さの大半になる
- 図形の計算はメニューを描いた後に回す（押せるまでの時間を床が遅らせない）
- 育つ演出は、本番を終えてメニューに戻った時の1回だけ。増えたタイルだけを、各フレームで順番が来た分だけ描き足す（描いたものは消さない）。終わったら土台に焼き付ける
- 起動直後・サーバーの値で追いついた時は演出しない。`prefers-reduced-motion` のときは演出せず完成形を描く
- 実測（CPU を1/6に落とした Chromium）：演出の最初か最後に1回、最大約0.7秒止まる。入力中には起きない。CZ1104 実機は未計測

## 6. 生成器の差し替え口

図形ごとに違うのは「タイルの一覧を作る」部分だけ。形式は `generators.js` の先頭に書いてある。

```
make({ W, H, ox, oy, edge, margin }) → [{ p: [[x,y],...], cls: 1|0, dir: 0..4, h?: [[x,y],...], o?: 0..1 }, ...]
```

`h` は穴（ドーナツ形の輪など）。描く側は `p` と `h` を1本のパスにして塗る（`h` は逆回りで渡す）。
穴を使う図形をサイトへ写すときは、サイトの共通エンジンの描き方も合わせる（算数タイムアタックの `floorPoly_` は対応済み）。

**育つ順の値 `o`**：タイルは `o`（0〜1。小さいほど先に育つ）を持ってよい。起点が複数の図形に使う。
`o` を持つ図形では、共通エンジンは育ち始める点からの距離ではなく `o` の順に並べる（1つの図形の中で、全部のタイルが持つか、全部が持たないかのどちらか）。
①の先のにじみは、距離ではなく枚数（次の60枚）で付ける。例：円と球（circlesphere）は、円と球それぞれの中の距離の順位を枚数で割った値を `o` にして、
2つが同じ割合ずつ交互に育つ。`sampler.html` と算数タイムアタックの共通エンジン（`floorGen_`・教師画面のプレビュー）は対応済み。

並べ替え（育ち始める点からの距離順）・薄め・3層・描画は共通エンジンが受け持つ。

tape・decagon・petals は、3年のTAの背景として提案した案（長さのたんい・大きな数・何倍でしょう）から利用者の評価で採用した。petals はいちど選外にした案の復活。

clockstar・pascal・chair・fibgrid・farey・padovan・decimal は、3年の残りの単元（時こくと時間・たし算とひき算の筆算・かけ算の筆算・表とグラフ・分数・三角形と角・小数）の背景として提案し、利用者の評価でストックとして採用した（どのサイトに入れるかは未定。入れるときに `COLORS.md` の台帳に足す）。
circlesphere は単元「円と球」のために、起点を2つにして円の模様と球の模様を並べた。モードに連動して片方だけ育てる案と見比べ、利用者の評価で「交互」（どのモードの正答でも2つが同じ割合ずつ育つ）を採用。球の明暗はプレビューのままでよいとの評価。

scaleswirl・scalefib は「ピル（長方形の短辺に半円）を基本の部品にした図形」の試作から採用した。帯の境の線のある／なし、端の重なりのある／なし、曲がる／曲がらないの8通りを見比べたうえで、「曲がる・境の線なし・重なりあり」を、さらに隙間なく（すき間のタイルを持たず）ピルだけで敷き詰め、ピルどうしで染め分ける形にした（`ideas/pills.js`）。
曲がったピルを「同心の2本の弧＋半円2つ」と決めると、帯の幅は帯の中で変えられない（区間の継ぎ目で端が重ならなくなる）。太りながら巻く対数螺旋の帯は、この部品では作れない。
見た目の評価のときの所見：fibgrid は格子縞に見えて神秘性は弱い。pascal はミントとすみれの明るさが近く、シェルピンスキーの三角形が読み取りにくい。decimal は petals と同じ対数極座標の渦で、同じ学年で並べると似て見える。

丸みのある3図形（whirl / flower / mandala）は、「丸みと神秘的な対称性」を求めた再試行の中から、利用者の評価で採用した。
丸い渦格子は最初、格子の辺をS字にしならせた鱗（楕円に近い形）だった。「重ね合わせはそのままに、楕円でなく真円が折り重なるように」との評価で、真円を重ねる今の形にした。単元「円と球」の背景の候補。

多重格子は方向の数を1つ変えるだけで別の図形になる（`GrowingFigures.multigrid(N)`）。図形の種類を増やす第一の手段。

各サイトでは、単元が図形を id で宣言する（算数タイムアタックは `UNIT.floorPattern`。`common/index.html` に `generators.js` を写してある）。
どのサイトがどの図形かは `COLORS.md` の台帳に書く。

## 10. 作り方の知見（試作で分かったこと）

- **対数極座標で作る**：螺旋・同心の図形は (s = log r, θ) で組み立てる。この座標では対数螺旋も円も直線なので、
  タイルは直線の多角形として作り、辺を細かく打ってから (x,y) に写すだけで曲線になる。円で切るのも半平面で切るだけ
- **仕切りで本数を2倍にする**：対数極座標のままだとマスは外ほど大きくなる。半径が2倍になる円（花びらの仕切り）ごとに腕の本数を2倍にすると、どこでも大きさが揃う
- **斜めに走る分を足す**：螺旋の一画の長さは、ねじれ t のぶん (1+t²) 倍に伸びる。一画の長さを揃えるときはこれを掛ける（入れ忘れると外の一画が細長くなる）
- **切った辺は弧として打ち直す**：(s,θ) で円に沿って切った辺を、両端だけ写して直線で結ぶと、隣のタイルとの間に隙間ができる（丸い渦格子で隙間0.4%）。切った辺だけ細かく打ち直す
- **画面の外は先に捨てる**：外側の帯は腕の本数が多く大半が画面の外。点を打つ前にタイルの中心だけで捨てる（生成 0.5秒 → 20ms）
- **特別な中心は円板で削る**：中心だけ別の形（同心円など）にするときは、格子のタイルから円板を取り除き、円の内側を輪で埋める（`minusDisk`）
- **真円は細かく打つ**：すき間の側を円の弧で削るなら、円のタイルも同じくらい細かい多角形にする（36角形では弦と弧の間の三日月形が積もって隙間0.3%）。120角形で解消
- **円の螺旋は対数極座標の正三角形格子で**：p·w1 + q·w2 = (0, 2π) を満たす60°のベクトル w1・w2 を取ると、右回り p 本・左回り q 本の螺旋に円が並ぶ（p・q にフィボナッチ数を使うとひまわりと同じ並び）
- **重ねて見せる図形は「手前の円を取り除く」で作る**：円を重ねた鱗は、各円から手前の円を順に取り除いた残りをタイルにする（重なりの順が決まれば、タイルは平面を隙間なく分ける）
- **穴のあるタイルは作れない**：小さな円が手前で、大きな円の中にすっぽり入ると、大きい方に穴が空く。仕切りの近くでは帯を先に比べ、内の帯（大きい円）を手前にする。小さい方が奥なら隠れて消えるだけで済む
- **Math.hypot は遅い**：点ごとの距離の比較は2乗どうしで比べる（丸い渦格子の生成が約3割速くなった）
- **近くを探す升目は数のキーで**：文字列のキー（'x,y'）と forEach の関数、「見た」を記す object は、ごみ集めを含めて生成時間の大半を食った。数のキーの Map と Int32Array の印に替えて約半分になった
- **取り除く弧の向き**：取り除く円の中心が相手のタイルの内側にあると、弧は長い向きに回る（大きな円から、中心が中に入った小さな円を取り除くとき）。短い向きの弧の中点がタイルの内側かどうかで決める（`minusDisk`）
- **小さな円を手前にしない**：内向きでも帯どうしは内の帯（大きい円）を手前にする。外の帯の小さな円の列を手前にすると、大きな円を横切って2つに切り分け、1枚のタイルにならない
- **画面に掛かるかは外接する四角で見る**：大きなタイル（外側の大きな円など）は、中心が画面の外でも一部が画面に掛かる。中心の位置で捨てると穴になる（`check.cjs` と `sampler.html` は外接する四角で見る。サイトの共通エンジンへ大きなタイルの図形を写すときは、そちらの捨て方も合わせる）
- **双曲の図形は円の外を鏡映で埋める**：円板の中のタイルを w → w/|w|² で円の外へ写すと、平面全体（リーマン球面の南北）を覆う。中心 0 は無限遠へ行くので、その頂点は両隣の向きの遠い2点に置き換える
- **双曲の図形は中央の数枚が大きい**：円板を画面より大きくすると、画面の大半が中央の数枚のタイルになり枚数が足りない（ファレイで56枚）。円を画面に収め、外を鏡映で埋めた
- **置き換えの図形は単位と見た目の大きさを分ける**：パドバンの渦のように大きさが指数で伸びる図形は、図形の単位をタイルの大きさと同じにすると画面に数個しか入らない。図形の単位を小さく取り、大きい部品だけをタイルの大きさに割る
- **扇ごとに先に捨てる**：対数極座標で帯ごとに扇を回すときも、扇の四隅が画面から遠ければ切り取りの前に捨てる（十進の渦：スマホで 549ms → 36ms）
- **同心円を両側で弦にすると重なりが出る**：隣り合う輪が同じ円を別々の点で打つと、弦のたるみの差が細い重なりになる（鱗のピルでスマホ 0.22%）。たるみを 0.03px 未満（角の刻み √(0.2/r)）にして解消
- **目で見る評価が決め手**：検査に合格した案の多くが、見た目の評価で落ちた。基準5・6は `sampler.html` で必ず見る

## 11. 根拠（設計に使った知見）

- 処理流暢性：対称・反復・規則は速く処理でき、その速さが快になる（Reber, Schwarz & Winkielman 2004）
- 複雑さと好みの逆U字（Berlyne）。中程度の複雑さが最も好まれる
- Kaplan の選好行列：部分的に隠れた「この先」が選好を最も安定して予測する（Mystery）→ ①の先のにじみ
- 意味の揺らぎからの発見（Muth & Carbon 2013「Aesthetic Aha」）→ 育つと規則（螺旋・花形）が浮かぶ
- 縞模様の視覚ストレス（Wilkins：高コントラストの等間隔の縞 約3周期/度）→ 縞・点滅は使わない
- 前庭障害と動き（WCAG 2.3.3）→ `prefers-reduced-motion` で演出を止める
- 黄金比が普遍的に好まれるという説は支持されない（→ 比率ではなく構造で美しさを出す）
